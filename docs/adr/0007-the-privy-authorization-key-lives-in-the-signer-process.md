# ADR 0007 — The Privy authorization key lives in the signer process

**Date:** 2026-08-31
**Status:** accepted
**Decides:** which Radar process holds the key that authorises Privy to sign,
and what it checks before using it.

## Context

[ADR 0005](0005-customers-keep-custody-and-grant-radar-a-bounded-signer.md)
settles that the customer keeps custody and grants Radar a bounded signer through
Privy. It does not say **where Radar's half of that arrangement lives**, because
until the API was read closely it was not obvious that Radar's half is a private
key at all.

It is. Privy's server API requires three things on a signing call:

| header | what it is |
|---|---|
| Basic auth | app id and app secret — a shared credential |
| `privy-app-id` | the application |
| `privy-authorization-signature` | **an ECDSA P-256 signature over the request** |

That last one is made with an *authorization key* whose private half Privy never
sees — it is generated by the app, and its public half is registered as a signer
on the customer's wallet. Verified against Privy's own specification: the payload
is `{version, method, url, body, headers}`, canonicalised per RFC 8785, hashed
with SHA-256, signed with ECDSA P-256, DER-encoded and base64'd.

So Radar holds a private key whose signature causes customer funds to move. That
is the same category of object as the wallet key `radar-signer` was built to
isolate, and the question of which process holds it is invariant 1's question,
not a deployment detail.

### Why this is not obviously the same as the local signer

Worth stating, because the analogy can be pushed too far. The local signer holds
a key that *directly* signs a Solana transaction. The Privy authorization key
does not sign a transaction; it signs an HTTP request that asks Privy to sign a
transaction. There is a policy engine in between, and it enforces the bound.

The reason that difference does not change the answer: the policy engine bounds
*what* may be signed, not *whether* Radar meant to ask. A compromised process
holding the authorization key can sign every request the policy permits, as fast
as it can make them — the policy is a ceiling on each request, not a statement
that any particular request was intended.

## Decision

**The Privy authorization key lives in `radar-signer`, and `radar-serve` never
holds it.** `radar-serve` asks the signer for a `privy-authorization-signature`;
the signer produces one only after re-decoding the transaction inside the request
and checking it against a kernel `Authorization`, exactly as it does today for a
local signature.

Three properties follow, and each is the reason for a corresponding refusal:

1. **The signer signs a request, never bytes.** The method takes a typed Privy
   request and an `Authorization`. It does not take a payload to sign. This is
   the same reason the signer refuses address lookup tables
   ([ADR 0003](0003-legacy-transactions-because-the-signer-must-be-able-to-read-them.md)):
   a signer with a method that signs what it is handed is a signing oracle, and
   the guarantee — *every account it authorises is one it read in the bytes it
   signed* — is exactly the property such a method destroys.

2. **The transaction is re-decoded from inside the request.** The signer parses
   the base64 transaction out of the Privy body itself, rather than trusting a
   copy passed alongside it. A caller that could hand over one transaction for
   checking and a different one for signing would make the check decorative.

3. **The canonicalisation refuses what it cannot canonicalise exactly.** RFC 8785
   specifies a number serialisation that is easy to get subtly wrong. Radar
   constructs these payloads itself and they contain no floats, so the
   canonicaliser handles the subset it needs and **errors** on anything else
   rather than emitting a nearly-right encoding. A signature over a payload that
   differs from what Privy reconstructs simply fails, which is safe; a
   canonicaliser that guessed would be a source of failures nobody could
   reproduce.

## What this costs

**A round trip on every signing call**, from `radar-serve` to the signer process
and back, over the same pipe the executor uses. On a path that already makes an
HTTPS call to Privy, a local pipe is not the cost that matters.

**More surface in the signer**, which is the part of the system with the least
of it, and that is a genuine loss. The signer's virtue is that it is small enough
to read completely. Adding a second signing mode makes it bigger.

The alternative was worse in a way that is hard to bound: `radar-serve` is the
process with a listener, a model provider, an HTTP client, an embedded frontend
and a paywall. It is the largest attack surface in the system and it is the one
process that should never hold a key.

**The shared credential is still in `radar-serve`.** The app secret and Basic
auth stay there, because they authenticate the *application* rather than
authorise a signature. This is a real limit on what this ADR buys: an attacker
with `radar-serve` can read wallet addresses and call every unsigned endpoint.
They cannot make a customer's wallet sign anything, which is the boundary that
matters.

## Consequences

- `radar-signer` gains one typed method and one new key type. It still has no
  network, no listener, and no method that signs arbitrary bytes.
- `radar-serve` gains a Privy client that can look wallets up and submit signed
  requests, and holds no key.
- The deployment gains a second key file, and both must be readable only by the
  signer's user. `RADAR_PRIVY_AUTHORIZATION_KEY` belongs to the signer process,
  never to `radar-serve` — a deployment that puts it in `radar-serve`'s
  environment silently discards this decision, so the signer refuses to start
  without it and `radar-serve` never reads it.
- Rule 8 applies as usual: no authorization key means no customer signing, not
  unsigned requests.

## What would reverse this

Evidence that the signer round trip is a material latency cost on a path where
latency changes an outcome. Given
[`0010`](../research/0010-the-considerations-document-classified.md) already
establishes that Radar does not compete on speed, that evidence is unlikely — but
it is the number that would do it.
